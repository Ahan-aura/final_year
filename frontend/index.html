          Multi-Session Sharing vs Data Isolation
        

        

          As formulated in the Capstone Abstract: "Multiple sessions may optionally share the validated repository while maintaining per-session data isolation."
        


        

          

            

              Shared Layer: Skill Repository
            

            

              When Session Alpha synthesizes and validates a new capability, it is promoted with visibility: shared.
            

            

              When Session Beta subsequently executes a similar task, it immediately discovers and reuses Session Alpha's validated code with zero synthesis cost and sub-10ms latency!
            

          


          

            

              Isolated Layer: Task Data & Files
            

            

              All raw task inputs, CSV data, uploaded proprietary records, and execution telemetry are strictly scoped by session_id.
            

            

              Session Beta has zero access to Session Alpha's raw records, uploaded files, or private session logs.

1. Connection to Base Paper (Pati, 2025)

          

            Our system operationalizes the survey paper's taxonomy of "learning agents" and "meta-reasoning agents" (Section III-C). It directly addresses the critical research gap highlighted in Sections IV-B-3 and VII-A: the lack of systematic, measurable evaluation frameworks for agent adaptation. Rather than relying on internal closed benchmarks, our workbench makes skill acquisition observable, verifiable, and measurable.
          

        


        

          
2. Capstone Viva Q&A Guide (Prepared for Reviewers)


          

            
Q1: How do you guarantee a "validated" skill is actually safe to reuse on new inputs?

            
A: Through our two-tier validation gate. First, the AST Security Guard prohibits dangerous modules (os, subprocess, network calls). Second, the code must achieve ≥90% accuracy on held-out test cases in an isolated execution sandbox before repository promotion.

          


          

            
Q2: What happens if a validated skill starts failing later (skill drift)?

            
A: The repository tracks per-skill success rates dynamically. If repeated failures cause a skill's success rate to fall below threshold, it can be automatically flagged for re-validation or retirement.

          


          

            
Q3: How is your skill discovery different from just caching LLM responses?

            
A: Response caching stores static outputs for exact prompt matches. Our skill discovery stores parameterized executable Python logic discovered via dense semantic embeddings and cosine similarity, generalizing across unseen inputs.

          


          

            
Q4: What is your sandbox actually isolating against?

            
A: It isolates against both malicious synthesis (preventing system file modifications, subprocessing, and network socket connections) and runtime bugs (infinite loops and hangs via thread execution timeouts).

          


          

            
Q5: Why these two domains specifically (tabular cleaning & code debugging)?

            
A: Tabular cleaning represents data-centric stateful transformations with clear statistical invariant checks, while code debugging represents symbolic algorithmic reasoning with deterministic pass/fail unit test suites.
